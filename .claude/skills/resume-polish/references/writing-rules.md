# 改写规则

## 每段经历的结构

阿酥 `/great-resume` 的顺序：**动作 → 系统能力 → 业务价值 → 结果证据 → 个人边界**。落到版面上：

```
公司条：Company · 正式职位                              日期
项目标题：一句话项目名 | 关键动作 · 关键动作 · 关键动作      （蓝色）
• 背景与目标：真实问题 + 目标（一行为宜）
• 我的职责：本人范围（有子要点时作为引导句）
  ○ 子动作：具体做法 → 产出/数字；
• 结果：可核验的结果
```

结果要分清性质：实际结果、团队结果、阶段结果、方案测算。测算不能写成"实现/带来"。

## 详略按强弱分配

先给每段经历按"与目标岗位的相关度 × 证据强度"排序，再分配行数：

- 最强的 1–2 个项目：6–7 行，带子要点；
- 中等：2–3 行；
- 弱相关：1 行（如早期银行实习、偏商业化的创业）；
- 开源/GitHub 项目：每个一行，整块放在项目经历最后。

超页时从最弱的开始删，不要平均地把每段都压扁。

## AI 产品经理版的用词

目标是让每段都读成"产品经理在定义和打磨 AI 产品"：

| 用 | 避免（解决方案/交付味） |
|---|---|
| 用户洞察、需求定义、PRD、验收口径 | 对接多方、统筹落地、现场实施 |
| AI 策略：模型/规则/人工的边界 | 方案交付、施工、按表施工 |
| 评测闭环：回归集、基线对照、Badcase、反向指标 | 交付与结果 |
| 指标体系、漏斗、A/B | Solution Lead、实施顾问 |
| 结果 | —— |

标题栏角色写 `AI Product Lead` / `Project Lead` 等中性或产品向称呼；求职意向写"AI 产品经理 ｜ 专长方向 · 专长方向"。

解决方案/FDE 版反过来：突出客户现场、痛点诊断、方案设计、原型、部署与交付。两个版本分开维护，不要把一边的措辞带进另一边。

## 诚信边界

- 公司名、正式职位、时间、学历保持真实；原职位名里没有 "AI" 就不加。
- 数字必须有出处（报告、仓库、用户原话）。照搬自其他版本、自己无法核对的，在交付说明中点名请用户确认。
- 从现有事实推出来的概括（如"AI 不直接对外输出结论"）可以写，但要在交付说明里标明是推断。
- 团队项目保留团队属性（"带 5 人团队"），不把团队结果写成个人结果。

## 让每条刚好满行的技巧

- 差 1–3 个字就多一行：删虚词（"的""进行""相关"）、合并并列项、去掉重复的限定语。
- 末行只有 40–70%：补一个**已有事实**里的细节（口径、对象、指标），而不是加空话。
- 引导句（"我的职责：……"后接子要点）允许不满行。
- 中文破折号、引号在 Times 字体下偏宽；实在卡字时换用更短的表达。
